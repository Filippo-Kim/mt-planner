## 1. 서비스 개요

### 1.1 한 줄 소개

학과 MT·소모임 행사를 처음 맡은 학생회 임원이, 인원·예산·일정만 입력하면 타임테이블과 준비물·예산 배분을 한 번에 받아보는 서비스.

### 1.2 배경 및 문제 정의

대학 학과 행사 기획은 대부분 인수인계가 제대로 이루어지지 않는다. 실제로 학과 MT를 준비하면서 다음과 같은 문제를 경험했다.

- 기획의 출발점이 없다. "MT 기획서 양식 어디서 구하지"부터 막힌다.
- 선배가 남긴 엑셀 파일에 의존하지만, 그 파일도 언제 만들어진 것인지, 어떤 기준으로 계산된 것인지 알 수 없다.
- 인원이나 예산이 변경되면 준비물 수량과 예산 배분을 전부 다시 계산해야 한다.
- 처음 맡는 사람은 "무엇을 빠뜨렸는지조차 모르는" 상태에 놓인다.

### 1.3 해결 방식

행사 정보를 입력하면 AI가 타임테이블·준비물·예산 배분을 한 번에 생성한다. 여기에 더해, AI 없이도 동작하는 준비물 계산기를 별도로 제공해 인원 변경에 즉시 대응할 수 있게 한다.

## 2. 타겟 사용자

### 2.1 주요 타겟

**학과 학생회 집행부 / 동아리 총무 (행사 기획 경험 1~2회 이하)**

- 20대 초중반 대학생
- 행사 기획을 처음 또는 두 번째로 맡음
- 참고할 만한 자료가 부족하거나, 있어도 신뢰하기 어려움
- 준비 기간이 짧고 다른 학업·활동과 병행해야 함

### 2.2 사용 시나리오

> 사회학과 학생회 총무 A는 9월 MT를 맡게 되었다. 참여 인원은 30명 내외, 회비는 1인 2만 원으로 정해졌다. 무엇부터 해야 할지 막막한 상태에서 MT Planner에 접속해 정보를 입력하고, 5분 만에 초안 타임테이블과 준비물 목록을 확보한다. 이후 집행부 회의에서 이 초안을 놓고 논의를 시작한다.

**핵심 가치: "0에서 1을 만드는 시간"의 단축.** 완성된 기획안을 제공하는 것이 아니라, 논의를 시작할 수 있는 초안을 제공하는 것이 목표다.

## 3. 페이지 구성

| 순서 | 페이지 | 파일 | 역할 | AI |
|---|---|---|---|---|
| 1 | 홈 | `index.html` | 서비스 소개, 핵심 기능 안내, 진입 유도 | — |
| 2 | 기획 시작하기 | `plan.html` | 행사 정보 입력 → AI 기획안 생성 | ○ |
| 3 | 준비물 계산기 | `checklist.html` | 인원수 입력 → 준비물 수량 자동 계산 | — |
| 4 | 소개 | `about.html` | 제작 배경, 사용법, FAQ | — |

### 3.1 네비게이션 방식

모든 페이지 상단에 공통 네비게이션 바를 배치하고, 현재 페이지는 `.active` 클래스로 강조한다. 별도 HTML 파일로 페이지를 분리해 구조를 명확히 하고, 각 페이지가 독립적인 URL을 갖도록 했다.

### 3.2 준비물 계산기를 AI 없이 구현한 이유

AI 호출은 응답 지연과 API 쿼터 소모를 동반한다. 인원수에 비례하는 단순 계산은 클라이언트에서 즉시 처리하는 것이 사용자 경험과 운영 비용 모두에서 유리하다. 또한 AI 기능에 장애가 발생해도 서비스의 일부는 계속 동작한다는 점에서 안정성 측면의 이점도 있다.

## 4. 핵심 기능: AI 기획안 생성

### 4.1 입력 명세

| 항목 | 형식 | 필수 | 예시 |
|---|---|---|---|
| 행사 종류 | select | ○ | MT / 세미나 / 답사 / 뒷풀이 |
| 인원 | number | ○ | 30 |
| 기간 | select | ○ | 당일 / 1박2일 / 2박3일 |
| 1인 예산 | number | ○ | 20000 |
| 컨셉·요청사항 | textarea | — | "술 안 마시는 사람 배려, 교수님 참석" |

### 4.2 출력 명세

AI는 아래 JSON 스키마로만 응답하도록 프롬프트에서 제약한다.

```json
{
  "timetable": [{ "time": "", "activity": "" }],
  "supplies": [{ "item": "", "quantity": "", "estimatedPrice": "" }],
  "budget": [{ "category": "", "amount": "" }],
  "totalBudget": ""
}
```

프론트엔드는 이 JSON을 파싱해 세 개 섹션(타임테이블 / 준비물 / 예산 배분)으로 렌더링한다.

### 4.3 사용자에게 제공하는 가치

- **시간 절약:** 백지 상태에서 초안까지 5분 이내
- **누락 방지:** 준비물과 예산 항목을 체계적으로 제시
- **조건 반영:** 예산 규모와 요청사항에 맞춘 현실적인 배분

## 5. 실패 처리 기준

### 5.1 처리 항목

| # | 상황 | 감지 위치 | HTTP | 사용자 안내 |
|---|---|---|---|---|
| 1 | 인원·예산 미입력 | 프론트 | — | "인원과 1인 예산을 입력해 주세요." (요청 전 차단) |
| 2 | 요청 형식 오류 | 서버 | 400 | "요청 형식이 올바르지 않아요." |
| 3 | 필수값 누락 (서버 검증) | 서버 | 400 | "인원과 1인 예산을 입력해 주세요." |
| 4 | 환경변수 미설정 | 서버 | 500 | "서버 설정 오류입니다. 관리자에게 문의해 주세요." |
| 5 | AI API 호출 실패 | 서버 | 502 | "AI 서버에 일시적인 문제가 있어요. 잠시 후 다시 시도해 주세요." |
| 6 | 응답 지연 (50초 초과) | 서버 | 504 | "응답이 지연되고 있어요. 다시 시도해 주세요." |
| 7 | JSON 파싱 실패 | 서버 | 502 | "결과를 처리하는 중 문제가 발생했어요. 다시 시도해 주세요." |
| 8 | 클라이언트 타임아웃 (55초) | 프론트 | — | "응답이 지연되고 있어요. 다시 시도해 주세요." |
| 9 | 네트워크 오류 | 프론트 | — | "네트워크 오류가 발생했어요. 다시 시도해 주세요." |

### 5.2 설계 원칙

**타임아웃은 계층별로 다르게 설정한다.** 프론트엔드 55초 > 서버 50초 > Vercel 함수 제한 60초 순으로 배치해, 안쪽 계층이 먼저 타임아웃되어 구체적인 에러 메시지를 전달할 수 있도록 했다.

**에러 상세는 사용자에게 노출하지 않는다.** API 응답 원문에는 내부 구조나 키 관련 정보가 포함될 수 있으므로, 사용자에게는 일관된 안내 문구만 표시한다.

**JSON 파싱 실패를 독립된 실패 케이스로 다룬다.** LLM은 지시에도 불구하고 설명 문장이나 마크다운 코드블록을 덧붙이는 경우가 있다. 서버에서 코드블록을 제거하는 전처리를 거치되, 그럼에도 파싱에 실패하면 별도 에러로 처리한다.

**요청 중에는 버튼을 비활성화한다.** 연타로 인한 중복 호출은 API 쿼터를 소모하고 사용자에게도 혼란을 준다.

## 6. 기술 구조

### 6.1 구성

- **프론트엔드:** HTML / CSS / JavaScript (바닐라)
- **백엔드:** Vercel Serverless Functions (Python, WSGI 인터페이스)
- **AI:** Google Gemini API (`gemini-3.6-flash`)
- **배포:** Vercel (GitHub 연동)

### 6.2 API 키 관리

API 키는 서버리스 함수의 환경변수로만 접근하며, 프론트엔드 코드에는 일절 포함되지 않는다. 브라우저에서 `/api/generate`를 호출하면 서버 함수가 키를 붙여 Gemini API로 중계하는 구조다.

`.env` 파일은 프로젝트 최초 커밋 시점부터 `.gitignore`에 등록해, 키가 커밋 이력에 남지 않도록 했다.

### 6.3 외부 SDK 미사용

Gemini SDK 대신 Python 표준 라이브러리 `urllib`로 REST API를 직접 호출한다. 서버리스 함수의 번들 크기를 줄이고, 의존성 변경에 따른 배포 실패 가능성을 낮추기 위한 선택이다.

## 7. 개발 과정에서의 주요 이슈

### 7.1 Vercel Python 런타임 인터페이스 변경

초기에는 `BaseHTTPRequestHandler` 기반으로 함수를 작성했으나, 현재 런타임은 WSGI 인터페이스를 요구해 실행에 실패했다. `app(environ, start_response)` 형태로 전환해 해결했다.

### 7.2 로컬 개발 서버와 배포 환경의 차이

`vercel dev`에서는 파이썬 함수 엔트리포인트 자동 감지가 반복적으로 실패했으나, 실제 배포 환경에서는 정상 동작했다. 로컬 에뮬레이터와 빌드 시스템의 동작이 다를 수 있음을 확인했다.

### 7.3 모델 버전 폐기

`gemini-2.0-flash` 호출이 404로 실패했다. 에러 응답 본문을 임시로 노출해 확인한 결과, 해당 모델이 폐기되고 후속 버전 사용을 안내하는 메시지가 포함되어 있었다. 모델명을 갱신해 해결했다.

**교훈:** 에러를 사용자 친화적 메시지로 감싸는 것은 운영상 옳지만, 디버깅 시점에는 원문을 확인할 수 있어야 한다. 임시 디버그 코드를 넣고 원인 확인 후 즉시 원복하는 방식이 유효했다.

### 7.4 함수 실행 시간 초과

출력이 길어질 경우 Vercel 함수 기본 제한 시간을 초과했다. `vercel.json`에서 `maxDuration`을 60초로 늘리고, 프롬프트에 항목 수 제한을 추가해 응답 길이 자체를 줄이는 방식으로 대응했다.
